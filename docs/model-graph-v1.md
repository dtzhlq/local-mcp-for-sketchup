# ModelGraph v1 and proposal-only existing-model edits

ModelGraph v1 is a versioned, model-revision-bound representation built from read-only adoption and structured snapshots. Full target materialization still uses `adopt_open_model(recursive=true)`, while an explicitly bounded proposal projection may use a narrower read-only structural probe without claiming a complete ModelGraph. The reasoning layer can propose but cannot authorize or execute a modification. P1 is verified with mock adoption, a committed queue-shaped golden fixture, a formal four-domain target-quality mock benchmark, Ruby source-shape tests, historical scoped live evidence, and current `.7/v1.4/definition-merkle.v2` Agent Gateway **read-only** runs. Earlier current-source runs used one byte-exact 5,859-occurrence disposable model and a weak-client profile to prove ambiguity abstention and unique structural selection. A later 71,360-occurrence Trimble S6 disposable model proved the bounded Group path: a complete 41/41 Group projection selected one top-level Group for review while materializing zero Face/Edge leaves and keeping the full graph explicitly incomplete. Every path kept `execution_allowed=false`. This remains `release_acceptance=false`; the formal cross-domain metrics are mock-only and are not a multi-real-SKP target-quality or native-mutation claim.

## Durable model store

`ModelGraphStore` persists graph history at model scope rather than task scope. A trusted runtime model identity is reduced to an opaque model key; raw model paths are not stored in the manifest. Saved source path is preferred over session document id, runtime object id, and version-level model GUID, so saving/reopening the same path can survive GUID renewal while two different paths with the same GUID remain isolated. Each model has a versioned manifest, content-addressed graph files, a current pointer, sequence numbers, revision metadata, and node/relationship deltas from the previous graph.

Writes are serialized across processes and use atomic replace plus integrity hashes. An unreferenced partial graph left before manifest publication can be replaced safely; once a manifest references a graph, content or manifest tampering fails closed. Stale owned locks can be reclaimed, but active locks are not bypassed. A restarted server can load the current or a historical graph, and concurrent identical persistence produces one version.

Queue persistence additionally requires a fresh read-only handshake whose plugin session, document id, opaque model identity, canonical occurrence contract, complete revision counts, model revision, and `model_modified` state exactly match the adoption result. Incomplete live revision coverage fails with `MODEL_REVISION_INCOMPLETE`; an adoption/handshake document switch fails with `MODEL_IDENTITY_MISMATCH`; revision or modified-state drift fails closed. The current source contract is capability `0.1.0-rc.3-capabilities.1`, manifest `2026-07-agent-contract-rc3.1`, `canonical-occurrence-path.v1`, and `definition-merkle.v2` with a 1,000,000 unique-entity safety limit. It also binds independently loaded SHA-256 attestations for `boolean_operations.rb` and `model_revision.rb` through capability, Session Contract, and transport-guard surfaces. A missing, stale, already-loaded, or load-boundary-changing source fails closed instead of silently satisfying the current contract.

`.7` retains the optional `structural-groups.v1` read-only projection introduced by `.6`: it projects bounded Group summaries, may attest explicitly requested Group paths with pure `manifold_report`, does not materialize Face/Edge leaves, and cannot authorize or execute a mutation. DSL version `1`, the 101-operation registry, and the 57-operation component scope are unchanged. `definition-merkle.v2` fingerprints reachable definition content once, incrementally hashes sorted entity fingerprints without retaining a second digest array, excludes process-local SketchUp `entityID` from stable identity, accepts only persistent IDs or unique Alma references, and fails closed on missing or duplicate entity/definition identities. Canonical JSON, Face loop/hole, and Edge endpoint ordering avoid representation-only drift while material, attribute, transform, and semantic geometry changes still change the revision. The materialized recursive target index keeps a separate caller-bounded limit. These current `.7/v1.4/v2` bindings are verified offline and now also have one fresh installed-plugin live read-only proof: exact 22-file installed/workspace bytes, two verified signed handshakes, complete `5859 / 5859` revision, `model_modified=false`, byte-stable disposable source, and a clean queue. This does not extend to mutation or release acceptance.

### Bounded Group proposal projection

`propose_existing_model_edit` chooses a discovery mode independently from execution authorization:

- `auto` is the guided/standard default. An explicit Group-scoped query such as `largest group` uses `structural_groups`; other target types retain `full_recursive` discovery.
- `structural_groups` requests `recursive=false`, `read_only=true`, `structural_groups=true`, and a caller-bounded limit no greater than 5,000. It records a `structural-groups.v1` projection with exact completeness/truncation metadata, model-world bounds, and `leaf_entities_materialized=false`.
- `full_recursive` remains an expert override when Face/Edge or mixed-entity evidence is required. Selecting it does not weaken revision, timeout, or completeness gates.

Projection nodes are `editable=false` and only `proposal_eligible=true`. A complete Group projection is sufficient solely for an explicit Group-scoped query whose proposed action is compatible with a Group. A truncated projection may resolve an exact returned Group path, but it must abstain from global ranking; a scope mismatch also abstains. The persisted graph retains `completeness.complete=false` with blocker `recursive_index_not_requested`, and the proposal records `bounded_structural_group_projection` evidence. No projection result can mint approval, enter the execution engine directly, or make model content trusted.

For a server-bound source proposal, a second structural probe may prepare the reviewed plan without materializing leaves only when every selected target is a canonical Group `pid:` path and every operation is a non-topology Group property operation (`rename`, material/visibility/transform, Tag, attribute, classification, or texture transform). Plan contract `.3` persists an `existing-edit-target-validation.v1` record, exact target count, projection completeness, and `leaf_entities_materialized=false`; the whole record is covered by both the plan hash and approval review-context hash. Direct callers cannot self-select this mode. The approved execution policy is also disclosed in the review context. Only a hash-bound, server-proposed, exact Group plan using `definition_wide` property edits may use bounded structural observations at Gateway preflight, apply preflight, iteration before/after, post-apply receipt binding, and finalization. `make_unique`, delete, cut, manifold, Boolean, Face/Edge, mixed-target, malformed, or otherwise incompatible work conservatively uses full recursive execution validation. Mock execution validates every phase through `existing-edit-execution-target-validation.v1`; the live record remains read-only until a new real-user approval is issued.

## Graph content

The graph persists:

- occurrence nodes using `canonical-occurrence-path.v1`, including real queue paths such as `pid:101.202.303`, parent paths, path segments, and parent-child hierarchy;
- component definition nodes and occurrence-to-definition membership;
- Face, Edge, object, and feature summaries;
- material, Tag, Scene, custom classification metadata, attributes, visibility, and bounding boxes when the runtime reports them;
- native SketchUp classification schema names/namespaces and per-definition opaque classification summaries;
- sibling spatial relations and geometry ownership/topology relations;
- shared-definition impact and allowed-operation contracts;
- model revision;
- strict completeness metadata for recursive indexing, including requested/total/indexed/truncated counts and blockers;
- optional server-verified PartGraph, ParametricRecipe, FeatureMappingPlan, evidence, and entity-path lineage references.

Only opaque artifact handles resolved and hashed by the server create trusted provenance edges. Artifact content remains untrusted data. Agent-supplied lineage strings are retained under `lineage.untrusted_claims` and never become trusted graph edges. Names, materials, Tags, classification, attributes, feature text, and future OCR fields are also explicitly untrusted. They can support candidate evidence but cannot modify workflow or execution policy.

SketchUp Ruby can enumerate loaded classification schemas, but it cannot enumerate which schema types are assigned to a component definition. ModelGraph therefore records `assignment_presence="unknown"`, `assigned_type_count=null`, `complete=false`, `values_exposed=false`, and blocker `assigned_schema_types_not_enumerable`. A hash of all definition attribute dictionaries participates in model revision without echoing their values. The implementation does not infer undocumented classification dictionary structure or call classification mutation APIs.

## Proposal task

Use the existing `start_agent_task` Gateway with:

```json
{
  "intent": "propose_existing_model_edit",
  "instruction": "Set the largest wall to the reviewed concrete material.",
  "interface_level": "guided",
  "inputs": {
    "runtime": "mock",
    "target_query": "largest wall",
    "action": "set_material",
    "parameters": { "material": "Reviewed_Concrete" }
  }
}
```

The task writes opaque handles for `model-graph.v1.json`, its model-level store manifest, and `existing-model-edit-proposal.v1.json`. The proposal contains candidates, structured evidence, confidence, exclusions, selected target only when unambiguous, shared-definition policy, operation proposal, risk, model revision, target-resolution status, and a full proposal hash.

`execution_allowed` is always `false`. A ready proposal returns a `next_action` carrying only an opaque server binding to the source task/proposal/hash/graph/revision. The reviewed task reloads the server-stored proposal, recomputes its hash, and rejects client-supplied target or operation overrides. Proposal parameters also reject reserved routing fields such as `op`, target references, scope, policy, and review metadata; `shared_policy` accepts only the contract enum. The reviewed task then creates a plan hash and trusted approval challenge; S2-S4 execution still requires a real user-presence token.

## Ambiguity behavior

The proposal remains in `awaiting_input` when any of these are unresolved:

- operation is not understood;
- an explicit `target_ref` is missing, nonexistent, duplicated, locked, or does not allow the operation;
- target description is missing or low-confidence;
- multiple candidates have similar evidence;
- required operation parameters are missing;
- a shared definition needs `make_unique` versus `definition_wide` choice;
- the evidence required by the requested target scope is truncated or otherwise incomplete. A complete bounded Group projection is sufficient only under the narrow rules above and never upgrades full-graph completeness.

Spatial superlatives are accepted only when their primary geometry metric has a unique winner, or when a metric tie is separated by at least the same evidence margin used by the ambiguity gate. An equal volume or equal directional coordinate is never resolved by `node_id`. Explicit structural descriptions such as `deepest geometry-bearing group` use server-derived topology counts and occurrence depth; model names and prompt text remain untrusted and cannot alter policy. Equal-depth structural candidates still return `multiple_similar_targets`.

`submit_agent_task_input` can add a `target_ref`, more specific `target_query`, missing `parameters`, or `shared_policy`. An explicit reference is exact-only: a missing reference never falls back to query ranking. Re-evaluation remains proposal-only. No target is sent to Existing Model Editing Engine until a separate reviewed task is created from the server-bound source proposal.

The selection contract additionally requires abstention when the geometry-deterministic largest target is locked or otherwise operation-ineligible instead of falling through to a smaller eligible target, and prevents untrusted model names from breaking equal-geometry ties.
