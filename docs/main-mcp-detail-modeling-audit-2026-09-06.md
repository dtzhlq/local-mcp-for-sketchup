# 主 MCP 精细建模审视与优化建议

审视日期：2026-09-06（Asia/Shanghai）。对象：`sketchup-mcp-replica` 主项目工作目录，当前分支 `codex/agent-contract-v1`，HEAD `4c01be89a0bc2c5a80884726a1662d1d470d05a7`。审视开始时有 95 个已跟踪文件修改、204 个未跟踪条目；以下结论以工作目录实际源码为准，不将它等同于 Git 的 main 分支或已发布插件。

**结论：现有底层足以支持明显更细的模型，但主流程没有把精细程度变成必须完成的任务。** 常用建筑 helper 有简化限制，组件、材质和局部切削在默认创建入口的组合不顺畅，验收又主要检查位置、身份和执行可靠性。因此，“能执行很多操作”与“能稳定交付精细室内外模型”之间存在实质缺口。

建议继续沿用本地 MCP、受控 DSL、Ruby 扩展、组件和现有参数追踪基础，将下一轮目标改为：**Agent 依据细节清单创建可编辑构件，按近景与实际几何逐项验收，缺项时继续局部修正。** 这比继续扩大粗略整场景样例数量更直接。

本次完成了主入口、工作流、几何执行、组件、材质、QA、测试样例和历史产物审查；运行 6 项相关离线回归，另做 2 组诊断复现。没有进入 live queue、修改当前 SketchUp 模型、安装插件或改动生产实现。本文件是审计及实施建议，尚未交付新的精细 SKP。

**最有说服力的证据来自两组可复现实验。**

第一组使用隔离 mock 状态，让默认 `create_model` 创建两个相互穿插的块体。布局 QA 明确返回 `ok=false`、`verdict=fail`、`layout.unexpected_collision`；Gateway 仍返回 `ok=true`、`task_state=completed`。源码在创建后调用 QA，却不根据 QA 结果改变完成分支。它证明“完成”当前不是质量达标。见 [创建流程](../src/agent-gateway.mjs) 第 1967–2000 行，以及 [本次复现结果](../output/detail-modeling-audit-2026-09-06/gateway-probe.json)。

同一组纯策略检查还确认：新建组件定义、新建材质、对刚创建部件切凹槽，都会在 Gateway 创建路线被拒。原因分别是可能覆盖已有定义、更新已有命名资源和属于既有模型编辑。这些限制有明确的保护目的；问题在于尚未识别“资源仅由本任务新建”的情况。完整 expert/edit 路线仍有相关能力，不能将其说成整个 MCP 不支持组件或 Boolean。见 [创建策略](../src/agent-dsl-policy.mjs) 第 8–65、117–175 行。

第二组直接调用当前 QA 函数，读取两套历史室内 queue snapshot，在内存构造保留包围盒、名称、QA/feature 声明与原警告的简化代理快照，移除细节几何数据。结果如下：

把规定岛台部件移出房间的负对照会失败，说明位置规则有效。另一个小型合成 reference QA 用例中，只要保留两个 feature 声明，去掉相应几何后仍通过；删除声明才失败。

此实验定位的是 **snapshot validator 对细节的盲区**。它没有在 SketchUp 中真实重建这些代理模型，也没有证明整条运行、身份、拓扑及保存检查都会被绕过。见 [实验脚本](../output/detail-modeling-audit-2026-09-06/quality-probe.mjs) 与 [完整结果及边界](../output/detail-modeling-audit-2026-09-06/quality-probe.json)。

**底层能力和实际限制需要分开看。**

当前 registry 对应 101 个 DSL 操作，57 个可用于组件定义，相关契约本次通过。带孔截面拉伸、mesh、匹配截面 loft、原生 Follow Me、真实 Boolean、组件实例、后续三维变换以及 PBR 已经存在。新的工作应利用这些能力，并补齐以下限制。

| 位置 | 当前实现与限制 | 对精细成果的影响 | 优化方向 |
|---|---|---|---|
| 建筑构件 | `architecture_operations.rb:269–290` 门窗直接建 box；`:175–193` 幕墙格、横梁、立柱合为 mesh，统一 frame material | 窗框、开启扇、压条、玻璃、收口不能随默认工具自动出现 | 构件拆成独立子部件，增加可复用门窗、柜体、幕墙节点配方 |
| 孔槽与倒角 | `product_operations.rb:112–138` 的 fillet/chamfer 是 XY 轮廓处理后竖向拉伸；`surface_operations.rb:204–217` screw_hole 是深色实体标记 | 能有“孔”的外观，却不保证是真孔；不能当任意边倒圆 | 显式区分真实特征、外观标记、代理体；详细级真孔真槽验收；先补常用截面/台面边缘 |
| 真局部切削 | `feature_operations.rb:118–133` 限定 Group、无变换、限定 kind，按 bbox 方向取面 | 旋转、嵌套、组件内的精细加工难直接使用 | 稳定面引用、局部坐标系、实例/定义编辑策略与几何后置检查 |
| 圆曲线精度 | cylinder 默认 16 段；管默认 8 段；栏杆硬编码 8 段，见 `primitive_operations.rb:375`、`surface_operations.rb:227`、`architecture_operations.rb:325–327` | 轮廓有明显折线；smooth 不能补回轮廓几何 | 按曲率、尺寸、观察距离和弦高误差决定分段，控制几何成本 |
| 扫掠与 loft | 旧 swept_path 截面固定 YZ；管框架每点选参考轴；loft 要求匹配点数、简单端盖，见 `surface_operations.rb:6–32,269–315` | 弯管、扶手和线脚可能扭转，凹截面端盖需增强 | 连续截面框架、起点方向对齐、重采样、可靠端盖及自交检查 |
| 墙角与场地 | `wall_path`、道路逐段生成独立体；斜墙 openings 在 JS mock 与 Ruby 分支有静态不一致迹象 | 墙角接缝、内部重复面、地形衔接难精确 | 连续偏移与 miter/bevel/round join；开洞 parity；道路/路缘截面与地形投射。斜墙问题需在隔离 live fixture 复验 |
| UV 与材质 | `object_operations.rb:237–241,601–608` 的 texture transform 只写属性；真正 face_uv 才尝试 position_material，失败为 warning | 木纹方向、瓷砖尺度和嵌套材质不能只靠 metadata 确认 | 真实 UV 投射、面级实际读回、纹理尺度、成功/失败覆盖统计 |
| 资产复用 | `alma_sketchup_mcp.rb:1387–1401` 加载 SKP 后立即 explode 根实例 | 不利于以完整可替换资产管理家具、灯具、植物 | 增加保留根组件的导入选择、本地资产索引、尺寸/轴向/面数/材质与来源信息 |
| 大量细节 | `primitive_operations.rb:6–44` 逐面 add_face；主要请求上限是 2,000 顶层操作，未形成面数与视距规划 | 高密度几何和逐块调用成本高，操作数不能代表模型负载 | 批量构造、共享定义、按对象分批、几何/纹理预算，实测建模/索引/捕获成本 |
| 小尺寸和修复 | 未见统一小细节放大构造策略；`boolean_operations.rb:496–503` 的显式 `seal_bbox` 会以包围盒替换失败实体 | 很小倒角建面需验证；某些“修复成功”会抹掉细节 | 按宿主容差验证小几何；精细模型验收排除破坏形状的包围盒替换 |

上述 Ruby 源码均位于 `sketchup_plugin/alma_sketchup_mcp/`。这张表的“限制”包括源码直接事实与已标注的待 live 验证项，不代表已经测得高密度性能瓶颈或统一的最小可建尺寸。

SketchUp 官方推荐使用 `EntitiesBuilder` 构造大量预定义几何；它不会像普通 add_face 一样自动求交切分，因此应作为经过拓扑校验的批量路径，不能机械替换全部建面。见 [官方几何生成指南](https://ruby.sketchup.com/file.generating_geometry.html) 和 [EntitiesBuilder](https://ruby.sketchup.com/Sketchup/EntitiesBuilder.html)。PBR 也已有官方接口和本项目实现，优化重点是实际材质与 UV 的完整落地。见 [Material API](https://ruby.sketchup.com/Sketchup/Material.html)、[Face UV API](https://ruby.sketchup.com/Sketchup/Face.html#get_UVHelper-instance_method)。

**上层需要把“做细”变成有状态的建模过程。**

当前 `workflows.mjs` 的创建路线主要是 DSL → build → layout QA，capture 可选；`PartGraph` 每个 part 主要编译成一个 primitive 加五类 feature 操作，尚未把装配、共享定义、实例阵列和细节依赖统一编译。它已有参数与身份追踪基础，适合扩展，没必要另起一套无法增量编辑的流水线。

建议采用以下完整过程：

```text
用途、尺寸、参考与目标观察距离
  → 部件树 + 必需细节 + 来源/假设 + 资源预算
  → 可复用构件定义与局部坐标
  → 主体尺寸与空间关系
  → 构造层次、连接、开口与收口
  → 小五金、曲面、接缝与真实材质
  → 总览 + 部件近景 + 必要剖视 + 实际几何检查
  → 缺项/缺陷定位到 part/feature → 局部修正
  → 保存、重开、再做一次参数修改
```

细节清单应包含 `part_id`、局部坐标、尺寸/容差、必需特征、表达方式、验证视图、来源和预算，并持久保存“还欠什么”。表达方式至少区分真实几何、纹理表达和代理体；真正影响轮廓、遮挡、连接和尺寸的细节优先用几何，木纹、微观粗糙度等使用纹理。软件内部可扩展现有 PartGraph/DesignIntent，不需要用户学习这些字段。

参考来源也要明确区分：按需求设计的模型允许记录合理设计假设；还原某一真实建筑则必须用尺寸、照片或图纸支持，不能把推断的背面、不可见节点或装饰细节写成已测事实。主 MCP 的精细生成不必等待图像重建子项目解决所有问题。

视觉方面已有两条粗结构路径：`visual-correction.mjs:519–523` 的基础比较缩到 128×128；另有 `background-normalized-visual-comparison.mjs:6–8` 默认 256 的前景配准与轮廓比较。256 路径目前作为附加诊断返回，最终 QA verdict 仍使用基础比较的 MAE 与前景质心条件（`visual-correction.mjs:279–287`）。应保留它们作为总览诊断，同时补上绑定对象的局部捕获、稳定相机、适当像素尺度和多视图。`reference-visual-qa.mjs` 中的部分 silhouette/area 指标实际上来自 bbox；feature 检查依赖声明，不应继续承担精细几何验收职责。

**建议按以下顺序实施，第一轮就产生可对比成果。**

| 顺序 | 具体交付 | 核心验收 |
|---|---|---|
| 1. 修正主入口与完成条件 | QA fail 不记质量完成；细节清单/未完成项；服务端确认的任务专属新资源范围 | 失败 QA、缺必需细节不能进入质量通过；本任务新组件/材质/局部加工可完成，既有资源保护保持有效 |
| 2. 建立通用装配与配方 | assembly、definition/instance、pattern、local frame、profile/feature 依赖；先做门窗、柜体、台面、扶手和线脚配方 | 改窗宽/柜宽能更新关联部件，重复构件共享定义，局部修改不重建全场景 |
| 3. 修复本轮构件暴露的几何与材质缺口 | 真开洞、框玻璃分材质、连续扫掠、适应尺度的分段、真实 UV | 剖视可见真孔；近景无明显折线/接缝错误；纹理方向和实际尺寸正确 |
| 4. 接通局部观察与质量循环 | 部件范围捕获、总览/近景/剖视、缺陷映射到稳定目标、修正后再验 | 故意缺失框扇、圆角、接缝或 UV 的负例能失败，补齐后通过 |
| 5. 扩展资产与规模 | 保留组件导入、本地资产目录、批量几何后端、模型成本规划 | 构件复用率、唯一几何成本、构造/索引/局部修改/捕获耗时可测；保存重开与质量保持 |

“任务专属新资源范围”是服务端可证明的对象所有权与范围，不是让 Agent 自报一个名称就获得更多权限；也不能简单删除现有 allowlist。精细建模主要依靠受控创建、特征和复用，任意 Ruby 调试权限不是这一轮优化的前提。

**新的测试数据应分成构件样片与完整场景，并真正测试 Agent。**

先建立 8 类小而严格的构件样片：窗框/扇/玻璃、门套/门扇/五金、柜体板件/抽屉/缝、台面开孔/水槽/边缘、弯扶手/立柱连接、阴阳角墙体/斜墙开洞、檐口/排水节点、砖石/木纹实际 UV。每类至少含尺寸变化、旋转或镜像、嵌套实例，以及故意缺特征的负例。这样可以准确判断问题是生成、材质、几何还是评估。

随后做两套主验收场景：

| 场景 | 必须可以近看与编辑的内容 | 建议观察与修改任务 |
|---|---|---|
| 室内：厨房与相邻生活区 | 柜体板厚/腔体、门板/抽屉缝、踢脚、台面边缘与真实水槽开孔、水龙头曲面、窗帘褶皱、灯具构造、材质尺度 | 总览；柜门/台面/水槽/窗节点近景；必要剖视；改变一段柜宽、台面开孔尺寸 |
| 室外：小型建筑入口、立面及前场 | 墙体转角、窗框进深/玻璃/压条、檐口或女儿墙层次、栏杆扶手连接、台阶收口、落水管、路缘/铺装与地形关系 | 街角与入口总览；窗/檐口/栏杆/铺装近景；改变窗宽、入口尺寸或立面分格 |

这里的目标可先设为用于近距离审看的设计表达模型，例如 0.5–2 米观察距离；这是建议的产品目标，不自动等于 BIM LOD 400 或可施工图深化。

每次真正验收应从冻结的需求、尺寸和参考开始，由 Agent 规划并调用 MCP 生成；手写固定 DSL 仅作运行层对照。保留不同尺寸、不同布置和未提前写死的测试场景，不能只靠同一脚本重复运行证明通用能力。

验收重点如下：

- 必需细节逐项通过，并有实际几何/面级数据、近景或剖视依据；不能由生成器自己写 `feature=true` 就算完成。
- 检查尺寸、开口、板厚、轮廓曲率、真实连接及材质尺度。碰撞先按语义接触分类，再对疑似问题做局部几何检查，避免把包围盒交叠全部当错误或全部豁免。
- 组件分层可编辑；重复构件复用；保存重开后结构、材质、身份和必要的视图一致；再次改参数仍有效。
- 负例必须检出：移除窗框、封死开孔、把圆角变直角、纹理尺度/方向错误、只保留 metadata、破坏共享实例的独立性。
